# 数据、配置表与持久化

## 数据所有权

| 数据 | 权威位置 | 访问边界 |
|---|---|---|
| 角色、背包、装备、技能、行会、邮件等 | 官方 SQL Server 及 M2 持久化链路 | 官方 API/工具；禁止平台直接修改核心表 |
| 怪物、物品、技能、地图、刷新、商城等静态内容 | 版本化源表与发布制品 | 单源生成服务器/客户端对应表 |
| 平台账号映射、订单、CDK、审计、发布 | 独立平台 DB（拟 PostgreSQL） | 平台模块内事务和受控 HTTP |
| 自有游戏活动变量 | 官方可用持久变量/受控扩展能力 | 能力矩阵定义保存语义；不默认即时落库 |
| 日志与统计 | 日志/分析系统 | 只读统计，不参与资产真值判定 |

官方表结构见[官方纯 Lua 数据库说明](https://engine-doc.996m2.com/web/#/30/3663)，该页面不能替代真实 schema 导出和迁移说明。

## 静态数据契约

Excel 为编辑入口，规范 CSV 为构建交换格式。提交策略需在 T02 统一：起步同时提交源表与规范 CSV，并用 source digest 检查导出一致；若团队不使用 Excel，则只提交 CSV。XLS/XLSX 读取库在实现时锁版。

每张表 schema 定义：字段名、类型、必填、默认、范围、枚举、单位、主键、引用、客户端/服务端可见性和 schema version。布尔值、空值、换行、分隔符和 Unicode 规范明确，不依赖 Excel 自动推断。列/行确定性排序，标识符与展示名称分离。

基础表建议：`item`、`monster`、`skill`、`buff`、`map`、`spawn`、`quest`、`activity`、`shop`、`recipe`、`attribute`。对接官方表时维护字段映射，不把这套拟定 schema 当作官方字段。

校验包括：ID 唯一、外键存在、技能/Buff 关联、地图/坐标边界、掉落权重有效、配方无非法自循环、商品价格/数量上限、资源路径存在、客户端/服务端公共投影一致。公式、外部链接和宏的处理策略显式规定；构建不执行表内脚本或宏。

## ID 与兼容

所有消息、物品、技能、属性、活动 ID 建注册表，记录所属模块、版本和是否废弃。ID 不复用；删除改为停用并给迁移行为。官方保留区间与自有区间在清点后确定，文档不先指定可能冲突的数字。

大整数账号/角色/订单 ID 以字符串交换；货币单位为整数最小单位，平台金额记录币种。禁止浮点金额和客户端自报余额。表格 ID 到官方内部 ID 通过映射实现，保持测试和生产映射一致。

## 编码

Git 自有文本 UTF-8 无 BOM。服务端部署字符集按锁定分支选择，当前[纯 Lua 官方页](https://engine-doc.996m2.com/web/#/30/1159)写明 GB2312；GBK 不能当作无差别替代。构建严格转换，再反向解码比对，输出不可编码字符的文件、行和列并失败。原始文本保持 UTF-8，部署字节哈希另外计算。

官方提供的历史编码文件先登记原始哈希，经可逆转换再纳入自有管理；没有把握的混合编码不得盲目修复。数据库连接字符集/排序规则、字段长度按实测记录，编码问题不能仅靠终端显示判定。

## 自有平台数据模型（逻辑设计）

| 表 | 关键字段/约束 |
|---|---|
| `account_mapping` | 渠道、外部 subject、自有账号；`(channel, subject)` 唯一，不以昵称关联 |
| `payment_order` | order ID、玩家/区服、渠道、币种/金额、商品快照、状态；渠道交易号唯一 |
| `payment_event` | 渠道回调标识、订单、签名验证结果、处理状态；事件去重，保存脱敏证据 |
| `reward_command` | command ID、order ID、目标、不可变奖励快照、状态、尝试/租约、结果证据；业务键唯一 |
| `outbox` | event ID、类型、payload digest、状态、下次重试；与业务状态同事务提交 |
| `cdk_campaign` / `cdk_claim` | 活动、码的安全摘要、期限、领取键、发货命令；唯一领取规则 |
| `audit_event` | 操作者、动作、目标、请求、结果、前后摘要、UTC 时间；追加写入 |
| `release` / `deployment` | release ID、BOM 哈希、环境、状态、操作者、结果和证据 |

奖励变更命令只由服务端可信模块构造。订单商品快照一旦支付确认不得随配置变更；发货结果单独记录，支付成功不等于已到账。

## 事务与迁移

平台 DB 内用唯一约束、事务和 outbox 保证本地状态一致；跨 M2 的一次资产变更必须单独验证。SQL Server 与平台 DB 不做直接跨库事务；不共享角色表供平台写入。

自有迁移编号、校验和、兼容范围、前置版本、锁时影响、备份要求进入 BOM。先扩展字段/读写兼容，再迁移与收缩。不可逆迁移不能用“回滚旧脚本”恢复，必须选择前向修复或经过演练的 DB 恢复；恢复带来的数据丢失范围明确。

官方基础库仅用官方迁移工具，保留迁移前备份、schema 摘要、工具哈希和验证报告。业务数据导出使用脱敏副本，不把生产备份写入 Git。

## 备份与数据保留

游戏库方案依据官方支持的 SQL Server 恢复模式配置，若需事务日志备份，必须正确建立完整恢复链；平台 DB 建单独备份/PITR 策略。至少月度隔离恢复演练，逐笔核对关键角色/订单/奖励与版本。保留时间、数据删除、审计访问策略在真实发行地区/业务确定后落实，不凭当前规划自行设法律结论。

## 数据交付的复用与开发边界

| 交付 | 来源/处理 | 验收 |
|---|---|---|
| 游戏基础 schema、角色/物品持久化 | 官方复用，官方迁移；本项目只登记版本/哈希与备份恢复 | R01/ENV03/CAP18，禁止平台写核心库 |
| 静态玩法表/资源清单 | 产品自制/合法来源；对接官方表的映射与校验自研 | SPEC01/V01/T02/T05，真实加载及双端 ID 一致 |
| 活动/任务/养成持久变量 | 官方公开变量能力复用，差异规则自研 | R07/R06，保存时点和资产事务边界实测 |
| 平台账号/订单/奖励记录 | 官方服务可用时保存必要映射/查询/审计；差异自研时才维护完整自有真值 | R08/P02—04，明确唯一执行/数据所有者 |
| 分析、部署和审计记录 | 现成采集/存储工具+项目事件/schema/流程 | P07/T09/OPS01，不参与游戏资产写入 |

上述平台表是候选逻辑模型，按 R08/P01 结论裁剪，不照搬或复制官方账号、背包、行会、邮件库。自有业务优先独立数据库；同机部署也不赋予写引擎 DB 权限。官方充值承担发货时，记录官方交易/结果引用用于核对，不再用自有 worker 给同一订单额外发货。
